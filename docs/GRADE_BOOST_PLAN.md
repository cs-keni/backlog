### Phase 1: Notifications (D+ → A)
**Priority: P1 — breaks the core value prop**

Files to build:
- `src/lib/notifications/dispatcher.ts` — main dispatcher: fetch matching users, check quiet hours, check notification_log, fire channels, batch digest
- `src/lib/notifications/email.ts` — Resend integration, digest email template (up to 10 jobs per email, ranked by Jaccard score)
- `src/lib/notifications/push.ts` — Web Push API, reads push_subscriptions, VAPID signing
- `worker/src/notifications/dispatcher.ts` — hook dispatcher into aggregator post-write
- Migration: `supabase/migrations/025_notification_log_schema.sql` — add `status text NOT NULL DEFAULT 'sent'`, `error text`, `channel text NOT NULL`; add unique constraint on `(user_id, job_id, channel)`

Matching logic: dispatcher filters by Jaccard score AND the user's saved feed filter state (`alert_match_threshold`, `location`, `remote_preference`, `salary_min`). If the user has no saved filters, fall back to Jaccard-only. This prevents noisy notifications from keyword overlap on unrelated roles.

Digest design:
```
One email per worker run (not per job).
One push notification per worker run (mirrors email digest — not per-job push spam).
Subject: "5 new jobs match your profile — {top company}"
Push body: "5 new matches — {top company}" with deeplink to feed.
If 1 job: subject "New match: {title} at {company}"
If 0 jobs: no email or push sent.
```

Failure behavior: if Resend or Web Push returns an error, write `notification_log` row with `status = 'failed'`. Do NOT mark as sent. Dedupe query: `WHERE status = 'sent'` — a 'failed' row does NOT block retry. Next worker run will retry. Log full error context (channel, user_id, job_id, error message).

Quiet hours handling: if a job arrives during a user's quiet hours, record it in a `pending_notifications` set for that user. On next worker run (outside quiet hours), process the missed jobs. Do NOT silently drop jobs that arrived during quiet hours.

Push 410/404 handling: in `push.ts`, if Web Push API returns 410 (Gone) or 404, DELETE the push_subscriptions row and write `notification_log` with `status = 'expired'`. This prevents dead subscriptions from accumulating.

Runtime requirement: `VAPID_PRIVATE_KEY` env var on the worker process (Render env vars). VAPID public key already stored in `public/sw.js` for the service worker. Add to Render dashboard before deploying Phase 1.

Tests:
- Unit: dispatcher threshold matching (Jaccard + filter state), quiet hours check, deduplication
- Unit: Resend error → no log row written as 'sent', function does not throw
- Unit: push 410 response → subscription row deleted from push_subscriptions
- Unit: dedupe: status='failed' row does NOT block retry (second attempt fires)
- Integration: new job inserted → dispatcher fires for matching user → log row written → second run same job does not resend

### Phase 2: Extension Core Gaps (C+ → A)

**2a: Workday async comboboxes**
File: `extension/src/content/fill-workday.ts` (extracted from fill.ts per Phase 2f decomposition)

```typescript
async function fillWorkdayCombobox(
  container: Element,
  value: string
): Promise<boolean>
  // 1. Click combobox trigger [role="combobox"] within container
  // 2. Wait for [role="option"] list via MutationObserver (1000ms timeout)
  //    — 500ms is too short for Workday on slow connections; use 1000ms
  // 3. Find option matching value (case-insensitive, starts-with fallback)
  // 4. Click match
  // 5. Return false on timeout (caller logs as skipped)
```

Cascading (country → state): after `fillWorkdayCombobox` for country resolves, attach a
`MutationObserver` to the state combobox container watching for `childList` changes.
When the state options list re-populates (or after a 300ms fallback delay), call
`fillWorkdayCombobox` for state. Do NOT use a fixed delay as the only strategy — it
fails on slow connections. The caller (`computeFills` Workday pass) runs a second
`fillWorkdayCombobox(stateContainer, profile.state)` after awaiting the country fill.

Fields to handle: country, state/province, work authorization, phone country code.

**2b: File upload**
File: `extension/src/content/fill.ts` calls background via message; background fetches.

Background↔content message protocol:
```typescript
// Content script sends:
{ type: 'FETCH_FILE', url: string, fileName: string }
// Background responds:
{ ok: true, buffer: ArrayBuffer } | { ok: false, error: string }
```

```typescript
async function fillFileInput(
  input: HTMLInputElement,
  fileUrl: string,
  fileName: string
): Promise<boolean>
  // 1. Send FETCH_FILE message to background (background fetches via fetch() — no CORS restriction)
  // 2. On { ok: true, buffer }: construct File from ArrayBuffer, add to DataTransfer, assign to input.files
  // 3. Dispatch 'change' event
  // 4. If input.files assignment throws SecurityError (sandboxed iframe): log SKIPPED,
  //    show user prompt in sidebar: "Attach resume manually — file upload blocked by this site"
  // 5. Return false on error (caller logs as skipped, never throws)
```

Extension background must proxy the fetch (content scripts can't fetch Supabase storage URLs cross-origin). `CORS` here means the browser blocks cross-origin `fetch()` from a content script context; background service workers do not have this restriction.

Cover letter upload: cover letters are job-specific (not profile-level). When `chrome.storage.session[tabId]` has a jobId (from Initiate-from-Backlog), the content script fetches `GET /api/applications?jobId=:id` to get the application's `cover_letter_url`. If no cover letter exists for this job, skip the cover letter input and log as SKIPPED in debug export. Resume always uploads from `profile.resume_url`. Manual extension launches (no jobId context) upload resume only.

**8a: Fix counter drift bug — daily_activity table approach**
`solved_at` is overwritten on re-solve, so any derivation from `lc_solves` is wrong for counting new-today problems. Both prior options ("move increment inside setSolves" and "derive from solves state") have the same re-solve bug. Correct fix: separate `daily_activity` table.

Migration: `supabase/migrations/024_add_daily_activity.sql`
```sql
CREATE TABLE daily_activity (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id uuid NOT NULL REFERENCES auth.users ON DELETE CASCADE,
  problem_slug text NOT NULL,
  date date NOT NULL,
  is_new_solve boolean NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
```
